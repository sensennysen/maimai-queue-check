## Goal

Add correctness and security guardrails that reduce the most likely regressions and boundary vulnerabilities, while preserving existing app behavior.

## Must-haves (goal-backward)
- Queue UI must not flicker or revert to the wrong branch/cabinet due to stale in-flight fetches.
- `/api/proxy` must no longer act as a general-purpose open proxy (SSRF + resource exhaustion controls).
- `/api/profile-meta` must be safe against XSS injection and resilient to host header poisoning.
- `npm test` remains green and deterministic (no external network, no live Supabase).

## Tasks

  <files>
    - src/hooks/useQueueData.js
    - src/hooks/useMonitorData.js
    - src/services/supabase/queue.js (optional, if adding AbortController plumbing)
    - src/__tests__/queue-stale-guard.test.jsx (new)
  </files>
  <action>
    In `src/hooks/useQueueData.js`:
    - Introduce request scoping using a monotonic `requestId` stored in `useRef`.
    - Apply the guard to:
      - the initial `loadInitialData()` fetch
      - the realtime-triggered refresh in `handleQueueChange`
    - Ensure only the latest request for the current `selectedBranch.id` + `selectedCabinet` can call `setQueue(...)` / `setError(...)`.

    In `src/hooks/useMonitorData.js`:
    - Apply the same request scoping pattern to `loadData()` and the realtime refresh path.

    Optional (only if low-risk and testable quickly):
    - Add AbortController plumbing:
      - Update `queueService.getQueueEntries(...)` to accept an optional `{ signal }` and pass it through any `fetch` call(s) used inside the service.
      - In each hook, abort the prior controller when starting a new fetch for a different selection.

    Add tests:
    - Create a unit test that simulates:
      - selection A starts request A (promise resolves late)
      - selection B starts request B (promise resolves first)
      - Assert state ends up at B and A’s late resolution is ignored.
    - Mock the `queueService.getQueueEntries` boundary to fully control timing.
  </action>
  <verify>
    <automated>npm test</automated>
  </verify>
  <done>

  </done>
</task>

<task id="01-02">
  <name>Harden `/api/proxy` with SSRF + timeout + size/content-type limits (SEC-01)</name>
  <files>
    - api/proxy.js
    - api/__tests__/proxy.test.js
    - src/pages/ExportBest50Page.jsx (only if needed to preserve behavior under stricter rules)
  </files>
  <action>
    In `api/proxy.js`:
    - Keep existing URL parsing and private/loopback/link-local blocks.
    - Add timeout (AbortController) for the upstream fetch.
    - Add response size limit:
      - If `content-length` is present and exceeds limit, reject.
      - While reading, stop once limit exceeded and return 413/502 (fail closed).
    - Restrict content-types to images only (e.g., `image/png`, `image/jpeg`, `image/webp`, `image/gif`; allow `image/*` if needed).
    - Decide and implement a host allowlist strategy:
      - Preferred: env-based allowlist (e.g., `PROXY_ALLOWED_HOSTS`) with a safe default list for known sources used by the app.
      - Ensure redirects do not bypass host checks (validate each hop or disable redirects).
    - Tighten CORS:
      - Prefer same-origin (no wildcard).
      - If the export route is same-origin, CORS can be omitted or set to a specific origin list.

    In `api/__tests__/proxy.test.js`:
    - Add enforced tests for:
      - timeout behavior (mock fetch to hang; ensure abort/4xx/5xx)
      - response size limit enforced
      - content-type rejection for non-image
      - host allowlist behavior (if allowlist enabled)
      - ensure SSRF blocks remain (localhost/private resolving)
  </action>
  <verify>
    <automated>npm test</automated>
  </verify>
  <done>
    - Proxy is no longer open-ended and is safe-by-default for the export image-localizer use case.
  </done>
</task>
